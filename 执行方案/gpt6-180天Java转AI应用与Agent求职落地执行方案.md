# Java 程序员转 AI 应用 / Agent：180 天执行方案

版本：2026-09-29（就业优先修订）  
适用对象：有 Java 后端经验、全职投入转型、主要求职中国大陆  
计划强度：每周约 42 小时，六天工作、一天完整休息；180 天约 1,080 小时。  
提醒：Offer 是目标，不是承诺。计划保证交付作品、持续投递和验证反馈；招聘结果还取决于经验年限、城市、学历、薪资范围和市场竞争。

**执行进度：第 1、2 天已完成。** 本次修订后，接下来从第 3 天继续，不重做已完成事项。修订重点是把求职和工程能力放在第一位；Agent 商业化不再作为这 180 天的验收目标。

## 0. 执行原则

1. **Offer 是第一目标。** 项目必须直接证明目标岗位需要的工程能力；第 2 周末开始做定向投递探针，随后持续准备面试，不能等项目“完美”后才求职。
2. **先用岗位证据选技术栈。** Java 是已有优势，但你贴出的 15 条样本中只有 4 条明确把 Java 列为可选语言，多条明确要求 Python/FastAPI。这个小样本不能代表全市场，但足以要求补 Python 后端基础，并在核验 30 条匹配的社招岗位后再决定项目主语言。
3. **只做一个求职作品项目。** 当前项目是展示 AI 应用工程能力的作品，不以证明商业需求或盈利为目的。项目场景可以继续用“JD—真实经历证据映射”，但不把它包装成已验证产品。
4. **Agent 不等于多 Agent。** 先用可解释的工作流、工具调用、人工确认和失败兜底解决问题。
5. **所有数字可追溯。** 评测数字、用户反馈、投递量、面试数、内容数据均保留原始记录；没有测过就不写成结果。
6. **内容是求职过程的副产物。** 每周做一条有实际技术结果或求职反馈的主内容；有余力再拆条，不为更新频率牺牲项目和面试准备。
7. **控制成本。** 先用现有电脑和免费工具，模型 API 设置用量上限；不先买 GPU、不先订一堆课程、不先付费投流。

## 1. 180 天结束时要交付什么

### 求职成果

- 3 份岗位画像：AI 应用开发、Agent/LLM 应用、Java + AI 后端；先建立 30 条去重、带链接和日期、符合本人社招条件的岗位样本，之后按月刷新。
- 1 份诚实的转型简历：保留真实 Java 工作经历；AI 主项目明确写作个人项目，列清职责、技术、指标和限制。
- 1 个可访问的作品集页，含代码仓库、架构图、演示视频、部署地址、评测说明、已知限制。
- 1 套面试题库：Java 后端 30 题、LLM/RAG 25 题、Agent/MCP/评测/安全 25 题；每题有自己的口头答案和项目例子。
- 每周持续投递与复盘；目标是拿到真实 Offer。没有 Offer 时，以投递—反馈—面试的漏斗数据决定下一轮，不把“完成计划”包装成求职成功。

### 主项目：AI 求职证据工作台（求职作品，不承诺商业化）

**用途：** 作为求职作品，证明你能设计并交付 LLM/RAG/工具调用/评测/权限控制的后端应用。不是 180 天内必须盈利的产品。  
**演示场景：** JD 写着一串技能，候选人把自己的真实项目材料放进来，系统将岗位要求映射到可追溯证据，并标记缺口。  
**输入：** 目标岗位 JD、本人简历、本人项目文档/代码说明、本人面试答案。  
**输出：** 可追溯的岗位要求—个人证据矩阵、证据缺口、建议补充的真实项目任务、针对 JD 的模拟面试与反馈。  
**技术展示重点：** 结构化抽取、RAG 引用、证据不足时拒答、受限工具调用、评测集、日志/成本/延迟、隐私和权限边界。面试中明确它是个人作品，不声称有真实用户、生产部署或商业验证。  
**MVP 边界：** JD/简历解析、要求结构化、证据检索和引用、缺口报告；模拟面试和 MCP 只有在核心链路稳定且目标 JD 确实需要时再加。前 180 天不自动投递、不替用户编经历。

### 评测指标

- JD 要求抽取：人工标注 50 条 JD，记录字段准确率。
- 证据检索：建立至少 100 个问题/证据对，记录 Recall@5、引用正确率和无证据时拒答率。
- 端到端任务：至少 50 条固定任务，记录完成率、人工修改率、平均响应时间、每任务模型成本。
- Agent：记录工具调用正确率、越权/危险操作拦截率、失败恢复率；写操作必须人工确认。
- 求职验证：记录岗位匹配度、投递回复率、面试进入率和被问到的技能缺口；用真实招聘反馈驱动下一轮学习。

## 2. 设备、账号、资料：先备齐这些就开始

### 必须有

- 电脑：能稳定运行 IntelliJ IDEA、Docker Desktop、浏览器和本地数据库；建议内存 16 GB 起、SSD 512 GB 起。已有电脑够用就不升级。
- 网络：稳定宽带；准备手机热点作为备用。
- 手机：录制竖屏内容和项目演示；现有手机即可。
- 麦克风：有线耳机麦克风即可；录音清楚比买相机重要。
- 账号：GitHub（或公开代码托管平台）、一个可接收模型 API 的账号、一个内容平台账号、一个求职邮箱。
- 文件夹：岗位 JD、简历版本、项目设计、代码评审/模拟面试记录、内容素材、周复盘、模型费用账单分开存。
- 纸笔或电子看板：一个任务看板就够，列为 Backlog / 本周 / 进行中 / 阻塞 / 已完成。

### 建议的软件

- Java、Maven/Gradle、IntelliJ IDEA、Git、Docker Compose、PostgreSQL + pgvector。
- Spring Boot + Spring AI；锁定与所用 Spring Boot 兼容的稳定版本，升级前先看官方文档和迁移说明。
- API 调试工具、Markdown、绘图工具、简单网页前端（选熟悉的 React/Vue 任一；不会前端先用模板，不在前端花超过一周）。
- 一个模型提供商 + 一个备用兼容接口；Embedding 可先使用同一生态中可用的模型。记录输入/输出 token 或供应商账单。
- 日志与可观测性工具选一个。敏感简历和访谈数据默认不写进公开日志、不放入公共测试集。

### 暂不购买

- GPU 台式机、付费训练营、多个 AI 编程助手、昂贵相机/灯光、付费云数据库、广告投流。
- 当免费额度或本地能力遇到真实瓶颈，再按瓶颈购买；每笔支出记下它解决的问题。

## 3. 每周工作制度：42 小时，有完整休息日

每周 6 天 × 7 小时有效工作，另留 1 天不安排学习、编码、投递或内容制作。每天可按以下节奏切分，午餐和休息不计入 7 小时：

| 时段 | 时长 | 做什么 |
|---|---:|---|
| 09:00–09:30 | 0.5h | 看板更新、写当天可验收目标 |
| 09:30–11:30 | 2h | 当周核心技术点，边看官方文档边做最小实验 |
| 11:30–12:00 | 0.5h | 写技术笔记：问题、选择、证据、未解决项 |
| 13:00–15:00 | 2h | 主项目编码 |
| 15:00–16:00 | 1h | 运行样例、评测、修复、补文档 |
| 16:00–17:00 | 1h | JD/简历/面试/内容，按阶段轮换 |

**每周分配基线：** 项目与工程 18 小时；针对项目的技术学习 8 小时；求职（简历、投递、面试）10 小时；自媒体 3 小时；岗位更新与复盘 3 小时。进入真实面试后，优先把项目时间转给面试准备。商业化访谈和收费试验不占本阶段固定工时。

**周日复盘只回答 5 个问题（30 分钟即可）：** 本周可展示的产物是什么？哪个数字真实变好了？哪个假设被推翻？下周最关键的一个交付是什么？哪件事应停止？

若连续两周睡眠、专注或情绪明显恶化，把有效工时降到 35 小时并保留休息日。多坐几个小时不会自动增加 Offer 概率。

## 5. 180 天逐周执行清单

每天 7 小时按上节时段拆分；下列每日任务说明这 7 小时的重点。每周第 7 天完整休息。第 26 周只有 5 个计划日（第 176–180 天）。

### 学习路径：按岗位能力依赖顺序，不按课程目录

每个技术主题都要当天进入代码或评测；课程只用于补当前任务卡住的知识。

1. **Python 服务端基础（先补到能开发 API，约 5–7 个学习日）**：虚拟环境和依赖、类型标注、Pydantic、异常处理、async/await、HTTP/REST、FastAPI、pytest。暂不学数据科学全家桶、PyTorch 或算法课。验收：自己写一个带输入校验、错误处理、单测和 Docker 启动说明的 API。
2. **LLM 应用基本功（约 2–3 周，包含集成和错误处理）**：模型 API、消息/上下文、结构化输出、流式响应、超时/重试/限流、密钥和成本记录。验收：JD 输入→符合 schema 的岗位要求，20 条人工标注样例可复跑。
3. **RAG（2–3 周做核心，最多再用 1–2 周修评测问题）**：文档清洗和切片、Embedding、向量检索、关键词/混合检索、引用溯源、权限过滤、无证据拒答。验收：先做 50 条问题—证据样例，记录 Recall@5、引用正确率和失败分类；指标稳定后停止打磨。
4. **工作流与工具调用（2–3 周做核心）**：先用普通代码明确步骤和状态，再加入 Function/Tool Calling；服务端负责权限、参数校验、幂等、超时、审计和人工确认。只有岗位样本或项目需求明确时再学 LangGraph、多 Agent、MCP；多出来的时间转给投递、面试和作品集解释。
5. **上线工程（持续迭代）**：Docker、配置隔离、日志/Tracing、回归评测、延迟与成本、降级、数据隔离。验收：别人按 README 能启动；能演示一次正常链路、一次失败链路和修复方式。
6. **Java 优势保留**：复用 Java、分布式、权限、消息和业务建模能力，不重新从零学后端。Spring AI 当前支持工具调用、RAG 与可观测性；是否将主项目实现为 Spring AI，要由 30 条符合本人条件的岗位统计决定，而不是因为你原来写 Java 就先入为主。

**主语言选择门（第 7 天前完成）：** 对 30 条去重、仍在招聘或近期发布、符合本人年限/学历/城市的社招 JD，分别统计“Python 硬要求”“Python 与其他语言择一”“Java/Spring 硬要求或明确加分”“Java 与其他语言择一”。根据符合条件的目标岗位数量和要求权重选择一个主实现栈；不要把一条岗位里“Python/Java/Go 任一”算成三条需求。若样本仍打平，默认用最短时间能做出可靠作品的 Java/Spring AI，同时把 Python/FastAPI 基础补到可读写服务。

### 第 1 阶段：市场和问题定义（第 1–14 天）

#### 第 1 周（第 1–7 天）：完成岗位核验与求职基线

- 第 1 天：已完成。经历清单按 Java、数据库、中间件、系统设计、业务成果分类；继续保留原始证据和可公开范围。
- 第 2 天：已完成。已有 15 条岗位样本；核对已有表格是否包含原始链接、采集日期、发布日期/更新日期、招聘类型（社招/校招）、经验、学历、城市和岗位状态，已有字段不重录，只补缺项。
- 第 3 天：核验这 15 条：去重、剔除过期/校招/算法训练类或本人明显不满足的岗位；将“必须、择一、加分、工作内容”分栏。无法找到原始页面的记录标为未核验，不计入频次。
- 第 4 天：再补 15 条符合本人实际条件的岗位；优先岗位原文或企业招聘页，限定目标城市和社招经验范围，不能只搜高薪 Agent 标题。当前贴出的样本全在上海；若求职城市不限定上海，分散到你愿意工作的城市。
- 第 5 天：统计 30 条岗位的技能频次和语言要求；选 10 条最匹配岗位做逐项缺口表：不会、了解、做过、能讲清、有可公开证据。
- 第 6 天：整理真实简历素材与 90 秒自我介绍。简历上的“6 年 Java / 1 年 Agent / 3 年架构”等年限必须逐项能由真实工作经历证明；若“1 年 Agent 落地”不是已发生的真实经历，立即删掉，改为“正在转型/个人项目实践”。
- 第 7 天：完整休息。

#### 第 2 周（第 8–14 天）：补后端缺口并启动作品

- 第 8 天：按学习路径补 Python 基础；若已熟悉 Python，则直接做类型标注、Pydantic、async/await 的小练习。
- 第 9 天：用 FastAPI 建一个最小 REST 服务，完成请求校验、统一错误响应和至少 3 条单测。
- 第 10 天：容器化该服务；写清如何启动、如何配置、如何验证。记录与 Java/Spring Boot 的对应概念，不重复学已掌握的后端知识。
- 第 11 天：根据岗位样本确定主项目主语言和框架；创建 AI 求职证据工作台仓库及一页范围说明，冻结 MVP 边界。
- 第 12 天：用真实但脱敏的本人经历做 10 条 JD—证据标注样例；无证据的条目标记缺口，不编故事。
- 第 13 天：拿简历和作品方向做 1 次模拟面试；开始 1–3 个低风险、高匹配投递探针，记录反馈，不等到第 35 天才接触市场。
- 第 14 天：复盘岗位数据、技能缺口、投递反馈和 Python 练习；按证据调整主攻岗位与项目技术栈。

**内容题目：**《我收集的 15 条 AI Agent 招聘，先删掉了几条：筛 JD 时发现的 3 个坑》。只说实际核验数量；未核验的链接、日期和招聘状态不作为事实发布。

### 第 2 阶段：模型调用与应用后端底座（第 15–35 天）

按第 7 天的岗位统计只选一个主实现栈：Java 路线使用 Spring Boot/Spring AI；Python 路线使用 FastAPI，并用一个熟悉的 Java 业务接口或既有经验讲清集成边界。不要为简历同时造两套完整实现。

#### 第 3 周（第 15–21 天）：模型 API 的最小闭环

- 第 15 天：初始化选定主栈的仓库，写 README、目录约定、配置管理和启动说明。
- 第 16 天：接入一家模型 API；密钥只放环境变量；完成一个最小问答接口。
- 第 17 天：记录请求 ID、模型名、耗时、错误类型；不把简历原文写进普通日志。
- 第 18 天：实现模型超时、重试上限、错误映射和友好报错；模拟断网与错误密钥。
- 第 19 天：给模型调用包一层自己的接口，业务代码不直接依赖具体供应商 SDK；选 Java 路线时用 Spring AI，选 Python 路线时用 FastAPI/Pydantic 管理服务边界。
- 第 20 天：做 10 条不同 JD 的手工输入演示；写下输出不稳定的例子和原因。
- 第 21 天：周复盘；整理第一篇技术文章草稿。

**内容题目：**《我没有先学算法：Java 后端转 AI 的第一个接口是什么？》

#### 第 4 周（第 22–28 天）：结构化输出和流式响应

- 第 22 天：定义岗位要求 JSON Schema：技能、年限、职责、必须项、加分项、证据来源。
- 第 23 天：实现结构化输出解析；验证失败时做一次受控修复，失败后返回可读错误。

#### 第 26 周（第 176–180 天）：总结和下一轮决策

- 第 177 天：整理项目最终发布版本：演示、架构、评测、局限、部署和停止条件。
- 第 178 天：公开转型复盘，区分事实、推测、失败和下一步；若没有 Offer，清楚写明。
- 第 179 天：根据漏斗决定未来 30 天：继续当前求职定位、回到 Java+AI 岗位、补技能或扩大城市。
- 第 180 天：根据 Offer 和求职漏斗决定未来 90 天：继续当前岗位方向、调整城市/职位范围或补具体短板。商业化另行决策，不作为本阶段成败标准。

## 6. 内容生产管线：每周 1 个主发布物

优先完成一条 3–6 分钟主视频或一篇技术复盘；精力有余再做 30–60 秒拆条。真实数据不够时发布过程、失败或假设，不编出结果。

每条内容先写 6 行：

1. 真实发生了什么（故事）。
2. 碰到的冲突/错误是什么。
3. 我做了什么具体实验。
4. 结果是什么，样本多少。
5. 观众可以复用的一条方法。
6. 下一步实验是什么。

建议轮换栏目：

- 《一条 JD 拆解》：本周岗位样本中的一个真实要求，附来源和日期。
- 《我做坏了什么》：检索错、输出错、部署错、面试答不上来。
- 《Java 后端视角做 AI》：复用超时、鉴权、日志、缓存、事务经验。
- 《项目实验周报》：一项指标的前后对照和限制。
- 《转型账本》：本周投入、产物、投递和反馈，数据未满样本时明确说明。

每周指标：按计划发布 1 条主内容；精力充足时再拆条。记录播放/完播/收藏/评论，但不挤占求职、面试和项目时间，也不把播放量当作求职能力或商业需求。

## 7. 求职管线：每周都有可执行动作

### 岗位筛选规则

- A 类：Java/Spring Boot 为主，并明确包含 AI 应用、RAG、Agent、MCP 或 AI 平台职责。
- B 类：LLM 应用/Agent/RAG 工程师，语言可 Java/Python；要求能用主项目证明关键链路。
- C 类：偏算法研究、模型训练、CUDA/GPU 推理的岗位，只有本人基础匹配才投，不为“AI”岗位名称盲目申请。

### 申请节奏

- 第 1 周：核验样本和真实经历，不追求投递量。
- 第 2–3 周：发出 1–3 个高匹配探针申请，尽早获得筛选反馈。
- 第 4–26 周：基线为每周 5–8 个定向申请；若已有真实面试流程，优先准备面试，不为完成数字盲投。连续两周没有回复时先复核岗位适配和简历，不单纯加量。

### 每个投递记录字段

公司、岗位原名、链接、发布日期、城市、年限、学历要求、岗位职责、匹配证据、缺口、简历版本、申请日期、联系人、阶段、反馈、下一步、拒绝原因（如有）。

### 面试验收

- 90 秒说清“我为什么转、我做了什么、我能解决什么”。
- 5 分钟说清项目数据流和架构。
- 20 分钟能追问到底：切片选择、检索评测、提示注入、权限、模型失败、成本、延迟、替代方案。
- 每个指标能说样本数、测量方法、基线、限制；没有真实生产数据就明确说是个人项目测试集。

## 8. 商业化：本阶段不设商业里程碑

- 180 天固定目标是求职、项目证明和公开记录转型，不要求 Agent 有用户、收入或商业验证。
- 若后续拿到 Offer 且每周仍有精力，再单独排产品访谈和收费试验；不能让商业化任务挤掉当期投递或面试。
- 当前作品只需在面试中讲清目标用户、任务、输入输出、成本和直接使用通用模型的替代方案。诚实承认“尚未验证商业差异”比编造用户数据更可信。

## 9. 明确不要做的事

- 不先学完概率论、深度学习、Transformer 数学推导课程；求职 JD 明确要求时按缺口补。
- 不同时学 Spring AI、LangChain、Dify、LlamaIndex 四套；主线一种框架，了解其他工具的边界即可。
- 不一上来做多 Agent、自主浏览器操作、自动投简历、自动发消息。
- 不把 RAG、MCP、Agent 当关键词堆在简历里；必须能现场演示、解释取舍和失败。
- 不做漂亮前端、复杂微服务、K8s、微调训练来拖延核心功能和投递。
- 不把私人简历、访谈记录、公司资料放进公开仓库或未经许可的第三方日志。
- 不以课程完成数、代码行数、视频播放量替代求职和用户价值。
- 不承诺“180 天必拿 Offer”，不将个人项目写成公司项目，不虚构薪资、用户、成交和效果。

## 10. 每周汇报模板

每周末给教练的输入控制在一页：

- 本周投入小时：实际值 / 计划值。
- 本周已完成：链接、截图、数字或录屏。
- 项目：新增功能、评测变化、最难失败。
- 求职：新增目标岗位数、投递数、回复/面试阶段、真实反馈。
- 内容：发布链接、真实数据、观众问题。
- 评审：代码评审/模拟面试次数、具体反馈、修复项和未解决项。
- 最大阻塞：一个。
- 下周承诺：项目一个、求职一个、内容一个。
