# Java 程序员转 AI 应用 / Agent：180 天执行方案

版本：2026-09-26  
适用对象：有 Java 后端经验、全职投入转型、主要求职中国大陆  
计划强度：每周约 42 小时，六天工作、一天完整休息；180 天约 1,080 小时。  
提醒：Offer 是目标，不是承诺。计划保证交付作品、持续投递和验证反馈；招聘结果还取决于经验年限、城市、学历、薪资范围和市场竞争。

## 0. 执行原则

1. **求职和项目并行。** 第 1 周就分析真实 JD；第 5 周开始少量验证性投递；第 10 周起进入稳定投递。
2. **Java 是主线。** 以 Spring Boot + Spring AI + PostgreSQL/pgvector 为主。Python 只补到能读懂、修改常见 AI 项目代码；岗位样本证明 Python 是目标岗位硬门槛时，再加深。
3. **只做一个主项目。** 不做多个互不相关的“炫技 Agent”。所有学习围绕一个真实垂直产品：AI 求职证据工作台。
4. **Agent 不等于多 Agent。** 先用可解释的工作流、工具调用、人工确认和失败兜底解决问题。
5. **所有数字可追溯。** 评测数字、用户反馈、投递量、面试数、内容数据均保留原始记录；没有测过就不写成结果。
6. **内容从真实过程产生。** 每周一条主视频加一条文字/短视频拆条，同步分发到适合的平台；不为日更牺牲项目。
7. **控制成本。** 先用现有电脑和免费工具，模型 API 设置用量上限；不先买 GPU、不先订一堆课程、不先付费投流。

## 1. 180 天结束时要交付什么

### 求职成果

- 3 份岗位画像：AI 应用开发、Agent/LLM 应用、Java + AI 后端；每份来自至少 30 条真实岗位记录。
- 1 份诚实的转型简历：保留真实 Java 工作经历；AI 主项目明确写作个人项目，列清职责、技术、指标和限制。
- 1 个可访问的作品集页，含代码仓库、架构图、演示视频、部署地址、评测说明、已知限制。
- 1 套面试题库：Java 后端 30 题、LLM/RAG 25 题、Agent/MCP/评测/安全 25 题；每题有自己的口头答案和项目例子。
- 每周持续投递与复盘；目标是拿到真实 Offer。没有 Offer 时，以投递—反馈—面试的漏斗数据决定下一轮，不把“完成计划”包装成求职成功。

### 主项目：AI 求职证据工作台

**首批用户：** 有 Java/后端经历、想应聘 AI 应用或 Agent 工程岗位的人。  
**痛点假设：** JD 写着一串技能，候选人难以把真实经历映射到证据，也不知道项目和面试补什么。  
**输入：** 目标岗位 JD、本人简历、本人项目文档/代码说明、本人面试答案。  
**输出：** 可追溯的岗位要求—个人证据矩阵、证据缺口、建议补充的真实项目任务、针对 JD 的模拟面试与反馈。  
**核心差异假设：** 保存每条 JD、每条个人证据及来源，能看到匹配理由和证据缺口；不只是一次性生成一段简历文案。差异是否成立，必须由用户测试验证。  
**MVP 边界：** JD/简历解析、要求结构化、证据检索和引用、缺口报告、模拟面试、人工确认后保存。前 180 天不自动投递、不替用户编经历、不做“全行业 AI 求职平台”。

### 评测指标

- JD 要求抽取：人工标注 50 条 JD，记录字段准确率。
- 证据检索：建立至少 100 个问题/证据对，记录 Recall@5、引用正确率和无证据时拒答率。
- 端到端任务：至少 50 条固定任务，记录完成率、人工修改率、平均响应时间、每任务模型成本。
- Agent：记录工具调用正确率、越权/危险操作拦截率、失败恢复率；写操作必须人工确认。
- 用户测试：至少 10 次真实目标用户测试，记录任务完成、卡点、是否愿意再次使用；没有证据就不宣称产品市场契合。

## 2. 设备、账号、资料：先备齐这些就开始

### 必须有

- 电脑：能稳定运行 IntelliJ IDEA、Docker Desktop、浏览器和本地数据库；建议内存 16 GB 起、SSD 512 GB 起。已有电脑够用就不升级。
- 网络：稳定宽带；准备手机热点作为备用。
- 手机：录制竖屏内容和项目演示；现有手机即可。
- 麦克风：有线耳机麦克风即可；录音清楚比买相机重要。
- 账号：GitHub（或公开代码托管平台）、一个可接收模型 API 的账号、一个内容平台账号、一个求职邮箱。
- 文件夹：岗位 JD、简历版本、项目设计、用户访谈记录、内容素材、周复盘、模型费用账单分开存。
- 纸笔或电子看板：一个任务看板就够，列为 Backlog / 本周 / 进行中 / 阻塞 / 已完成。

### 建议的软件

- Java、Maven/Gradle、IntelliJ IDEA、Git、Docker Compose、PostgreSQL + pgvector。
- Spring Boot + Spring AI；锁定与所用 Spring Boot 兼容的稳定版本，升级前先看官方文档和迁移说明。
- API 调试工具、Markdown、绘图工具、简单网页前端（选熟悉的 React/Vue 任一；不会前端先用模板，不在前端花超过一周）。
- 一个模型提供商 + 一个备用兼容接口；Embedding 可先使用同一生态中可用的模型。记录输入/输出 token 或供应商账单。
- 日志与可观测性工具选一个。敏感简历和访谈数据默认不写进公开日志、不放入公共测试集。

### 暂不购买

- GPU 台式机、付费训练营、多个 AI 编程助手、昂贵相机/灯光、付费云数据库、广告投流。
- 当免费额度或本地能力遇到真实瓶颈，再按瓶颈购买；每笔支出记下它解决的问题。

## 3. 每周工作制度：42 小时，有完整休息日

每周 6 天 × 7 小时有效工作，另留 1 天不安排学习、编码、投递或内容制作。每天可按以下节奏切分，午餐和休息不计入 7 小时：

| 时段 | 时长 | 做什么 |
|---|---:|---|
| 09:00–09:30 | 0.5h | 看板更新、写当天可验收目标 |
| 09:30–11:30 | 2h | 当周核心技术点，边看官方文档边做最小实验 |
| 11:30–12:00 | 0.5h | 写技术笔记：问题、选择、证据、未解决项 |
| 13:00–15:00 | 2h | 主项目编码 |
| 15:00–16:30 | 1.5h | 运行样例、评测、修复、补文档 |
| 16:30–17:30 | 1h | JD/简历/面试/内容/用户访谈，按阶段轮换 |

**每周分配基线：** 项目与工程 24 小时；技术补课 7 小时；求职 5 小时；用户/内容 4 小时；周计划复盘 2 小时。主项目进入开发期后，技术补课时间继续下降。

**周日复盘只回答 5 个问题（30 分钟即可）：** 本周可展示的产物是什么？哪个数字真实变好了？哪个假设被推翻？下周最关键的一个交付是什么？哪件事应停止？

若连续两周睡眠、专注或情绪明显恶化，把有效工时降到 35 小时并保留休息日。多坐几个小时不会自动增加 Offer 概率。

## 4. 阶段总览与阶段验收

| 阶段 | 天数 | 核心工作 | 进入下一阶段的验收 |
|---|---:|---|---|
| 1. 市场与定位 | 1–14 | 采样岗位、访谈用户、定目标和项目范围 | 60 条 JD 标签完成；至少 5 位目标用户访谈；确定 1 个主岗位方向和 1 个备选 |
| 2. LLM 应用底座 | 15–35 | Spring AI、模型接入、结构化输出、流式 API、错误处理 | 能运行一个 Java 服务：JD 输入→结构化岗位要求；有 README、架构草图、错误处理记录 |
| 3. RAG 求职证据 MVP | 36–70 | 文档解析、pgvector、检索、引用、评测 | 可用的 MVP；100 条检索样例；Recall@5/引用正确率/拒答率有基线；至少 3–5 次小规模定向投递 |
| 4. Agent 与 MCP | 71–105 | 工具调用、状态流、人工确认、MCP、安全、可观测 | Agent 完成受限的求职准备流程；50 个固定任务评测；高风险写操作不可绕过人工确认 |
| 5. 部署、用户验证、简历作品集 | 106–140 | 部署、用户测试、修复、公开作品集，稳定求职 | 至少 5 位用户完成测试，完整作品集可访问；每周 5–8 个定向申请并复盘 |
| 6. 面试与商业验证 | 141–180 | 强化面试、职位漏斗、人工服务试验、阶段总结 | 有持续面试管线；完成至少 10 次用户测试；决定是否继续、转向或开始小规模人工服务 |

阶段验收是继续前进的检查点，不是没达标就暂停全部工作。没过门时先定位阻塞项，一周内补最小缺口。

## 5. 180 天逐周执行清单

每天 7 小时按上节时段拆分；下列每日任务说明这 7 小时的重点。每周第 7 天完整休息。第 26 周只有 5 个计划日（第 176–180 天）。

### 第 1 阶段：市场和问题定义（第 1–14 天）

#### 第 1 周（第 1–7 天）：盘点与基线

- 第 1 天：写真实工作经历清单，按 Java、数据库、中间件、系统设计、业务成果分栏；注明哪些数据可公开。
- 第 2 天：从招聘网站收集 15 条大陆 AI 应用/Agent/LLM/RAG/Java+AI JD，保存链接、日期、城市、年限、硬技能。
- 第 3 天：再收集 15 条 JD；把重复词频和“必须/加分/工作内容”分开。
- 第 4 天：从中选 10 条最接近本人经历的 JD，计算缺口：不会、了解、做过、能讲清并有证据。
- 第 5 天：选择主攻岗位（先选 AI 应用/Java+AI 之一）和一个次级岗位；写目标城市、可接受薪资区间、学历/年限限制。
- 第 6 天：搭建 GitHub 仓库、看板、岗位表、用户访谈记录模板；录一段 2 分钟当前技术自我介绍，保存为基线。
- 第 7 天：完整休息。

#### 第 2 周（第 8–14 天）：验证用户问题

- 第 8 天：补足 60 条 JD；统一标签：Java/Python、RAG、Agent、MCP、数据库、部署、评测、安全、年限。
- 第 9 天：邀请 3 位 Java/后端转 AI 的目标用户做 20 分钟访谈；只问他们最近一次求职准备过程。
- 第 10 天：再访谈 2–3 人；整理原话，区分“抱怨”与真实付费/使用行为。
- 第 11 天：归纳最多的 3 个问题，提出“证据映射报告”这一单点产品假设。
- 第 12 天：写 1 页产品说明：用户、痛点、输入、输出、成功指标、隐私边界、拒绝功能。
- 第 13 天：请 2 位受访者看原型草图；记录哪里不懂、他们会拿什么替代、是否愿意用真实资料测试。
- 第 14 天：阶段复盘，确认下一阶段只学完成 JD 结构化所需的模型调用。

**内容题目：**《转 AI 第 1 周，我先看了 60 条 JD：Java 后端最常被要求补什么？》只报实际统计，注明样本来源和限制。

### 第 2 阶段：模型调用与 Java 应用底座（第 15–35 天）

#### 第 3 周（第 15–21 天）：模型 API 的最小闭环

- 第 15 天：新建 Spring Boot 仓库，写 README、目录约定、配置管理和启动说明。
- 第 16 天：接入一家模型 API；密钥只放环境变量；完成一个最小问答接口。
- 第 17 天：记录请求 ID、模型名、耗时、错误类型；不把简历原文写进普通日志。
- 第 18 天：实现模型超时、重试上限、错误映射和友好报错；模拟断网与错误密钥。
- 第 19 天：给模型调用包一层自己的接口，业务代码不直接依赖具体供应商 SDK。
- 第 20 天：做 10 条不同 JD 的手工输入演示；写下输出不稳定的例子和原因。
- 第 21 天：周复盘；整理第一篇技术文章草稿。

**内容题目：**《我没有先学算法：Java 后端转 AI 的第一个接口是什么？》

#### 第 4 周（第 22–28 天）：结构化输出和流式响应

- 第 22 天：定义岗位要求 JSON Schema：技能、年限、职责、必须项、加分项、证据来源。
- 第 23 天：实现结构化输出解析；验证失败时做一次受控修复，失败后返回可读错误。
- 第 24 天：写 20 条 JD 样例，人工标注期望字段，测字段准确率并保存错误样例。
- 第 25 天：实现流式输出接口；前端显示生成状态和可取消状态。
- 第 26 天：测试空输入、长文本、乱码、格式不完整和提示词注入样例。
- 第 27 天：把 prompt、模型参数、样例版本化；做一次 60 秒屏幕录制。
- 第 28 天：复盘结构化输出错误，不追求提示词“神句”。

**内容题目：**《让大模型稳定返回 JSON，我记录了它最常见的 5 种失败》

#### 第 5 周（第 29–35 天）：MVP 外壳与首次岗位验证

- 第 29 天：做最简网页：粘贴 JD、提交、显示结构化要求；前端只服务演示。
- 第 30 天：实现任务状态、请求追踪、异常提示；整理 API 示例。
- 第 31 天：给产品说明加上明确的隐私和数据删除说明。
- 第 32 天：拿 3 位用户的脱敏 JD 做可用性走查；让他们自己操作，不代替他们。
- 第 33 天：按真实 JD 缺口更新简历；写清个人项目，不把它冒充工作经历。
- 第 34 天：做 1 次技术模拟面试；针对项目从需求、设计、失败、成本四方面回答。
- 第 35 天：投 1–3 个高度匹配的岗位作为市场反馈探针；记录是否回复、拒绝原因或无反馈，不因样本小下结论。

**阶段验收：** 可运行 Java Web 原型；JD 结构化抽取有 20 条人工标注集；有 1 份真实简历初稿；完成至少 1 次模拟面试。

### 第 3 阶段：RAG 证据检索与 MVP（第 36–70 天）

#### 第 6 周（第 36–42 天）：资料摄取与数据模型

- 第 36 天：设计用户、JD、要求、证据文档、证据片段、评测样例的数据表。
- 第 37 天：实现文本/Markdown 上传；PDF 只做常见文本型文件，复杂 OCR 暂缓。
- 第 38 天：清洗页眉页脚、空行、重复文本；保存文档来源、版本和页码/段落位置。
- 第 39 天：做文件类型、大小、用户归属校验；失败时给出具体错误。
- 第 40 天：做删除接口和删除验证；测试数据隔离。
- 第 41 天：准备本人公开项目说明和合成示例资料，不导入公司机密。
- 第 42 天：写数据流图和文档解析限制。

#### 第 7 周（第 43–49 天）：Embedding 与向量检索

- 第 43 天：在 Docker Compose 中启动 PostgreSQL + pgvector；写可复现配置。
- 第 44 天：把证据片段生成向量并保存；向量维度不匹配要明确报错。
- 第 45 天：实现按用户/项目过滤的相似度检索。
- 第 46 天：用 30 个问题做纯向量检索基线，人工标注相关证据。
- 第 47 天：实现 Recall@5 计算脚本或 SQL 汇总；保存原始查询和结果。
- 第 48 天：给回答返回证据标题、段落或链接，不允许只显示“模型说”。
- 第 49 天：复盘哪些问题搜不到，先修数据和切片，不急着换数据库。

**内容题目：**《RAG 不是接上向量库就完成：我的第一版检索为什么找错证据》

#### 第 8 周（第 50–56 天）：切片、引用、无证据处理

- 第 50 天：实现按标题/段落切片的第一版；保留原文位置。
- 第 51 天：比较两种切片长度，每种跑相同 30 个问题。
- 第 52 天：回答时强制引用证据片段；无法引用时输出“当前资料无法证明”。
- 第 53 天：把 JD 要求与证据做结构化映射：有证据、弱证据、无证据三类。
- 第 54 天：写 20 个无证据问题，检查是否会编造履历。
- 第 55 天：邀请 2 位用户看报告；记录他们能否验证每个判断。
- 第 56 天：合并修复结果，发布内部 MVP 版本。

#### 第 9 周（第 57–63 天）：提高召回与排序

- 第 57 天：加入关键词检索基线，与向量检索结果对照。
- 第 58 天：实现简单混合召回；固定相同样例比较 Recall@5。
- 第 59 天：在确实有改善需要时接入一个重排器；记录额外耗时和成本。
- 第 60 天：做失败分类：资料缺失、切片错误、关键词不同、检索排序差、模型误读。
- 第 61 天：每类挑 5 个失败样例，逐个修数据/算法并比较前后。
- 第 62 天：整理 RAG 架构图、数据流、成本估算方法。
- 第 63 天：公开一次真实实验记录；结果不好也照实发布。

#### 第 10 周（第 64–70 天）：RAG 评测与第一次投递迭代

- 第 64 天：扩充到至少 100 个“问题—相关证据”检索样例。
- 第 65 天：统计 Recall@5、引用正确率、无证据拒答率，附人工判定方法。
- 第 66 天：针对低分项做一次迭代，不同时换多个组件。
- 第 67 天：做 API 延迟和单任务模型成本测量；记录样本量及硬件/网络限制。
- 第 68 天：完善简历项目条目：问题、本人实现、可复现指标、明确限制。
- 第 69 天：投 3–5 个适合岗位；逐条记录技能匹配与被拒/无反馈情况。
- 第 70 天：阶段验收和路线修正；若 JD 主要要求 Python，决定补多少，不盲目重写项目。

## 6. 内容生产管线：每周 2 个发布物

一个实验生产两个成品：一条 3–6 分钟主视频，另做一条 30–60 秒拆条或一篇短文。真实数据不够时发布过程、失败或假设，不编出结果。

每条内容先写 6 行：

1. 真实发生了什么（故事）。
2. 碰到的冲突/错误是什么。
3. 我做了什么具体实验。
4. 结果是什么，样本多少。
5. 观众可以复用的一条方法。
6. 下一步实验是什么。

建议轮换栏目：

- 《一条 JD 拆解》：本周岗位样本中的一个真实要求，附来源和日期。
- 《我做坏了什么》：检索错、输出错、部署错、面试答不上来。
- 《Java 后端视角做 AI》：复用超时、鉴权、日志、缓存、事务经验。
- 《项目实验周报》：一项指标的前后对照和限制。
- 《转型账本》：本周投入、产物、投递和反馈，数据未满样本时明确说明。

## 7. 求职管线：每周都有可执行动作

### 岗位筛选规则

- A 类：Java/Spring Boot 为主，并明确包含 AI 应用、RAG、Agent、MCP 或 AI 平台职责。
- B 类：LLM 应用/Agent/RAG 工程师，语言可 Java/Python；要求能用主项目证明关键链路。
- C 类：偏算法研究、模型训练、CUDA/GPU 推理的岗位，只有本人基础匹配才投，不为“AI”岗位名称盲目申请。

### 申请节奏

- 第 1–2 周：样本和画像，不以投递量为目标。
- 第 3–5 周：建立简历与面试基线，第 5 周少量验证性投递。
- 第 6–10 周：每周 3–5 个高度匹配申请。
- 第 11–20 周：每周 5–8 个定向申请，优先复盘反馈。
- 第 21–26 周：保持 5–8 个高适配申请；已有面试时优先面试准备而非盲目加量。

### 每个投递记录字段

公司、岗位原名、链接、发布日期、城市、年限、学历要求、岗位职责、匹配证据、缺口、简历版本、申请日期、联系人、阶段、反馈、下一步、拒绝原因（如有）。

### 面试验收

- 90 秒说清“我为什么转、我做了什么、我能解决什么”。
- 5 分钟说清项目数据流和架构。
- 20 分钟能追问到底：切片选择、检索评测、提示注入、权限、模型失败、成本、延迟、替代方案。
- 每个指标能说样本数、测量方法、基线、限制；没有真实生产数据就明确说是个人项目测试集。

## 8. 商业验证：不先做 SaaS

- **第 1–2 周：** 访谈 5–8 位目标用户，确认具体最近行为，不先推销。
- **第 6–10 周：** 用 MVP 让 3–5 人完成一项任务；看能否节省时间、找到真实证据、改变行动。
- **第 11–20 周：** 逐步累计至少 10 次用户测试；记录再次使用、推荐、主动询价，不把点赞当需求。
- **第 21–23 周：** 只试一项人工服务。若有人愿意付费，记录交付边界和成本；没有就调整问题或停止收费试验。
- **第 180 天决策：** 只有重复问题清楚、有人反复使用、人工交付流程稳定且有真实付费信号时，才把服务产品化；SaaS 后置。

## 9. 明确不要做的事

- 不先学完概率论、深度学习、Transformer 数学推导课程；求职 JD 明确要求时按缺口补。
- 不同时学 Spring AI、LangChain、Dify、LlamaIndex 四套；主线一种框架，了解其他工具的边界即可。
- 不一上来做多 Agent、自主浏览器操作、自动投简历、自动发消息。
- 不把 RAG、MCP、Agent 当关键词堆在简历里；必须能现场演示、解释取舍和失败。
- 不做漂亮前端、复杂微服务、K8s、微调训练来拖延核心功能和投递。
- 不把私人简历、访谈记录、公司资料放进公开仓库或未经许可的第三方日志。
- 不以课程完成数、代码行数、视频播放量替代求职和用户价值。
- 不承诺“180 天必拿 Offer”，不将个人项目写成公司项目，不虚构薪资、用户、成交和效果。

## 10. 每周汇报模板

每周末给教练的输入控制在一页：

- 本周投入小时：实际值 / 计划值。
- 本周已完成：链接、截图、数字或录屏。
- 项目：新增功能、评测变化、最难失败。

- 内容：发布链接、真实数据、观众问题。
- 用户：访谈/测试人数、任务完成、重复使用/付费意向原话。

- 下周承诺：项目一个、求职一个、内容一个。

## 11. 市场依据与限制（截至 2026-09-26 检索）

- 2026-09-21 发布的一条 AI Agent 招聘信息列出 Prompt、RAG、Function Calling、外部 API 和效果评测；职位要求中还提到 Python，说明 Java 背景并不自动替代目标岗位的 Python 门槛。该岗位是单条样本，不能代表整个市场。
- 天津一条 AI 应用/RAG 招聘信息描述了 Spring Boot 业务集成、文档解析、切片、Embedding、混合检索、Rerank、生成、评估、MCP/Tool Use、可观测性；它也要求完整 RAG 项目和后端经验。
- 阿里巴巴一条 2026 年秋招 AI 应用研发岗位把 Java/Spring Boot、Agent Harness、工具调用、上下文/记忆/权限/观测和 RAG 结合；它明确面向 2027 届，不能把校招条件当作社招岗位的普遍要求。
- Spring AI 官方文档覆盖模型 API、Vector Store、Tool Calling、MCP 和可观测性；因此本方案选它作为 Java 主线。用到的具体版本应随项目启动时官方稳定版本和兼容矩阵选择。
